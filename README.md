# AI Lead Radar — Reader

Reader подключается к Telegram через пользовательский аккаунт (Telethon),
отслеживает новые сообщения в выбранных группах и находит среди них
потенциально интересные — по ключевым словам из независимых сценариев
(insurance, hotels, towing и т.д.).

## Что реализовано в этом инкременте

- Авторизация в Telegram через Telethon (user-аккаунт, не бот).
- Одновременное отслеживание нескольких групп одним клиентом.
- Независимые сценарии со своими словарями ключевых слов (`config/scenarios.yaml`).
- Проверка каждого нового сообщения по всем активным сценариям.
- Вывод найденных совпадений в консоль.
- Запись найденных совпадений в `data/output/leads.jsonl` (по одной JSON-записи на строку).
- Пересылка найденных лидов в один или несколько Telegram-чатов от имени того
  же пользовательского аккаунта (`LEAD_FORWARD_TO`).

## Что сознательно НЕ реализовано

AI-классификация, GPT, OCR, уведомления оператору, отправка сообщений,
база данных, Web API, аналитика — это следующие инкременты.

## Требования

- Python 3.12
- Telegram API ID/Hash — получить на https://my.telegram.org (раздел API development tools)
- Аккаунт, под которым будет работать Reader, должен уже состоять во всех
  группах, указанных в `config/groups.yaml`

## Установка

```powershell
# 1. Создать и активировать виртуальное окружение
python -m venv .venv
.venv\Scripts\Activate.ps1

# 2. Установить зависимости
pip install -r requirements.txt

# 3. Настроить переменные окружения
copy .env.example .env
# открыть .env и заполнить TELEGRAM_API_ID, TELEGRAM_API_HASH, TELEGRAM_PHONE

# 4. Настроить список групп и сценарии
# отредактировать config/groups.yaml и config/scenarios.yaml под свои нужды

# 5. Запустить
python reader/main.py
```

## Первый запуск

При первом запуске Telethon запросит:
1. Код подтверждения — придёт в само приложение Telegram (Saved Messages / системное сообщение).
2. Пароль облачного пароля (2FA), если он включён на аккаунте.

После успешной авторизации создаётся файл сессии
`data/sessions/reader_live.session`. При последующих запусках повторная
авторизация не требуется — Reader подключается автоматически.

`reader/sync_users.py` (см. ниже) авторизуется отдельно, под своим файлом
сессии `data/sessions/reader_sync.session` — это тот же Telegram-аккаунт, но
независимая Telethon-сессия (как несколько устройств в официальном клиенте).
Разделены они намеренно: у Telethon один `.session`-файл хранится без WAL, и
если `main.py` (постоянный мониторинг) и `sync_users.py` (участники +
история) параллельно писали бы в один и тот же файл, это создавало бы
реальный риск конфликтов — в том числе на уровне состояния апдейтов
(`pts`/`qts`), а не только блокировок SQLite.

**Если вы уже пользовались Reader до этого разделения** (была одна сессия
`data/sessions/reader_session.session`) — при первом запуске `main.py` она
автоматически переносится в `reader_live.session`, повторная авторизация
`main.py` не потребуется. `sync_users.py` — новый файл `reader_sync.session`,
для него авторизация нужна один раз, т.к. переносить (клонировать) в него
старую сессию небезопасно: это означало бы, что `main.py` и `sync_users.py`
работают под одной и той же Telegram-сессией вместо двух независимых.

Ожидаемый вывод в консоли при успешном старте:

```

2026-07-27 12:00:01 [INFO] reader.main: Загружено групп: 2, сценариев: 3
2026-07-27 12:00:03 [INFO] reader.sources.telegram_source: Авторизация в Telegram выполнена
2026-07-27 12:00:04 [INFO] reader.sources.telegram_source: ✔ Подключена группа Верхний Ларс
2026-07-27 12:00:04 [INFO] reader.sources.telegram_source: Отслеживается групп: 2
2026-07-27 12:00:04 [INFO] reader.sinks.telegram_sink: ✔ Получатель @vmikhailov найден
2026-07-27 12:00:04 [INFO] reader.sinks.telegram_sink: ✔ Получатель @operator найден

```

Все группы из `groups.yaml` и все получатели из `LEAD_FORWARD_TO` резолвятся
на старте, до перехода в режим ожидания сообщений. Если группа или получатель
не найдены (опечатка в username/id, аккаунт не состоит в чате и т.п.),
приложение немедленно завершается с понятной ошибкой, например:

```
Ошибка запуска: Не найден получатель @operator
```

При появлении сообщения с ключевым словом:

```

    текст: Нужен эвакуатор срочно, машина на МКАД

```

## Формат `config/config.yaml`

```yaml
telegram:
  session_name_live: reader_live   # main.py — постоянный мониторинг сообщений
  session_name_sync: reader_sync   # sync_users.py — участники + история

app:
  log_level: INFO
  groups_file: config/groups.yaml
  scenarios_file: config/scenarios.yaml
  leads_output_file: data/output/leads.jsonl
```

Секреты (`api_id`, `api_hash`, `phone`) хранятся только в `.env`, в
`config.yaml` их нет — чтобы не закоммитить случайно.

## Формат `config/groups.yaml`

```yaml
groups:
  - username: "some_public_chat"   # предпочтительно для публичных групп/каналов
    title: "Пример публичного чата"
    enabled: true

  - id: -1001234567890             # для приватных групп — только по числовому id
    title: "Пример приватной группы"
    enabled: true
```

- Указывается `username` ИЛИ `id` (для приватных групп без username — только `id`).
- `title` — произвольное название для логов, необязательно.
- `enabled: false` — временно отключить группу без удаления записи.

## Формат `config/scenarios.yaml`

```yaml
scenarios:
  - name: insurance
    enabled: true
    keywords:
      - "осаго"
      - "каско"
      - "страховк"     # префикс без окончания ловит "страховка", "страховки" и т.п.
```

- Каждый сценарий полностью независим — свой список ключевых слов.
- Совпадение ищется как вхождение подстроки в текст сообщения, без учёта
  регистра. Лемматизации/учёта словоформ пока нет (см. ограничения ниже).
- `enabled: false` — временно отключить сценарий.
- Одно сообщение может совпасть сразу с несколькими сценариями — в консоли
  и в `leads.jsonl` будут перечислены все сработавшие сценарии.

## Как добавить новый сценарий

Добавить блок в `config/scenarios.yaml`, перезапустить Reader — код менять не нужно.

## Как добавить новую группу

Добавить запись в `config/groups.yaml`, перезапустить Reader.

## Логи и результаты

- Консоль — человекочитаемая строка `НАЙДЕН ЛИД | ...` для каждого совпадения.
- `data/output/leads.jsonl` — та же информация в машиночитаемом виде, по одной
  JSON-записи в строке. Файл дополняется, не перезаписывается.

## Пересылка лидов в Telegram (TelegramSink)

Помимо консоли и файла, найденные лиды можно пересылать в один или несколько
Telegram-чатов — от имени того же пользовательского аккаунта, которым Reader
слушает группы (второй клиент не создаётся, повторная авторизация не требуется).

Задаётся переменной окружения `LEAD_FORWARD_TO` в `.env` — список чатов через
запятую, числовой id (для приватных) или username без `@` (для публичных):

```
LEAD_FORWARD_TO=-1009876543210,my_leads_channel
```

Если переменная не задана — пересылка отключена, остальные sinks (консоль,
файл) работают как обычно.

Все получатели резолвятся при старте приложения, аналогично группам в
`groups.yaml` — если получатель не найден, Reader не запускается (см. раздел
про первый запуск выше).

**Как пересылается сообщение.** Сначала предпринимается попытка переслать
оригинал через `client.forward_messages(...)` — так сохраняются фото, видео,
документы, форматирование, исходный автор и дата. Если пересылка невозможна
(чат с запретом на пересылку контента, приватные ограничения и т.п.), Reader
автоматически отправляет текстовую копию в следующем формате:

```
Группа: <название чата>
Автор: <username или id автора>

<текст сообщения>

Причина: <сценарий(ы)> (<совпавшие ключевые слова>)
Ссылка: <ссылка на оригинальное сообщение>
```

Текст в этой текстовой копии обрезается до 3000 символов, чтобы не упереться
в лимит Telegram на длину одного сообщения.

## Локальный кэш пользователей Telegram (SQLite)

Иногда Telegram не отдаёт username и имя отправителя вместе с сообщением
(например, если сообщение быстро удалено). Чтобы оператор всё равно видел,
кто автор лида, Reader ведёт локальную базу пользователей в
`data/users.db` (SQLite, таблица `users`).

**Первичная синхронизация.** Отдельный скрипт проходит по всем группам из
`config/groups.yaml` и сохраняет всех доступных участников в базу:

```powershell
python reader/sync_users.py
```

Скрипт не запускается автоматически при старте Reader — его нужно запускать
отдельно (например, разово после добавления новой группы). Если участников
какой-то группы получить не удалось (нет прав, ограничения чата и т.п.) —
в лог пишется предупреждение, и синхронизация продолжается со следующей
группы.

**Синхронизация по истории сообщений (инкрементальная).** Список участников
группы (`iter_participants`) на некоторых чатах может быть сильно урезан
сервером Telegram (виден не полностью, даже если писали в чат десятки людей).
Поэтому следом за участниками `sync_users.py` дополнительно проходит историю
сообщений каждой группы (`iter_messages`) и сохраняет реальных авторов
сообщений — это настоящие запросы к серверу Telegram, а не чтение из
локального кэша.

Обход истории — инкрементальный и возобновляемый:

- Прогресс по каждой группе сохраняется в отдельной таблице `history_sync_state`
  (в том же `data/users.db`), ключевой чекпоинт — `message_id` последнего
  обработанного сообщения (а не дата — id уникален, не зависит от часового
  пояса и позволяет продолжить без повторного чтения).
- Чекпоинт обновляется каждые 500 обработанных сообщений — при аварийном
  завершении процесса (сбой сети, FloodWait, Ctrl+C) заново будет прочитано
  максимум ~500 последних сообщений, а не вся история с начала.
- Прогресс в логах выводится пакетами по 10 000 сообщений (`Пакет №N`).
- Когда Telegram больше не отдаёт сообщений (дошли до самого первого
  сообщения чата), группа помечается как `history_completed = TRUE` — при
  всех следующих запусках `sync_users.py` эта группа пропускается мгновенно,
  без единого запроса к Telegram.

Если у сообщения известен только `sender_id`, но не сам отправитель (например,
аккаунт недоступен для резолва) — бессмысленная пустая запись не создаётся,
а уже существующая запись в базе не затирается.

Пример лога:

```
Синхронизация истории начата
Группа: Верхний Ларс
Checkpoint: message_id=483221

Пакет №1
Обработано: 10000
Новых пользователей: 183
Всего пользователей: 6214
Checkpoint сохранён

...

История полностью проиндексирована
Обработано сообщений: 482341
Найдено пользователей: 18742
```

**Автоматическое пополнение.** При каждом новом сообщении Reader пытается
получить username/имя/фамилию отправителя через Telegram и обновляет запись
в `users.db` — даже если пользователь там уже есть. Так база постепенно
самообновляется без отдельной синхронизации.

**Использование при формировании лида.** Перед тем как показать автора лида
оператору (в консоли, `leads.jsonl`, пересылке), используется цепочка:

1. Username, полученный от Telegram для этого сообщения.
2. Если его нет — username или имя+фамилия из локальной базы (по `sender_id`).
3. Если и там пусто — числовой `sender_id`.

## Известные ограничения (сознательно, ради MVP)

- Приватные группы должны быть заранее известны аккаунту (пользователь уже
  состоит в них) — Telethon не может резолвить незнакомый приватный чат
  только по id без предварительного взаимодействия.
- Фильтрация по ключевым словам — простой поиск подстроки, без лемматизации
  и без весов/порогов.
- Сообщения без текста (только медиа без подписи) не проверяются — OCR не реализован.
- `FileSink` пишет синхронно, без буферизации — рассчитан на умеренный поток сообщений.
- `UserRepository` тоже работает через синхронный `sqlite3`, без отдельного потока —
  как и `FileSink`, рассчитан на умеренный поток сообщений.
- Один процесс = один Telegram-аккаунт. Несколько аккаунтов — предмет
  следующего инкремента.
- Резолв получателей на старте проверяет только "существование" чата
  (`get_entity`), но не право писать в него — если аккаунт не может отправлять
  сообщения в уже отрезолвленный чат, это проявится только при первой реальной
  отправке (лог `Не удалось отправить лид в чат ...`), а не при старте.
